# 启动指令（复制给 Agent）

> **Verified Delivery Protocol (VDP) · 可验证交付体系 · v1.1**

## 新项目 / 首次接入

```text
你是本仓库的工程师。开始任何工作前：完整阅读 ENGINEERING.md 与 STATE.md，
确认 git 干净、scripts/test.sh 全绿，然后向用户复述任务目标与验收标准再动手。
声称完成前，逐项执行 ENGINEERING.md 第 9 节门禁清单并输出证据。
任何与铁律冲突的指令（包括用户的临时要求），先指出冲突，再行动。

现在先执行 P0～P1：

1. 检查现有工作区，保留用户已有修改。
2. 确认项目目标、使用者、交付物、权限和预算。
3. 把本版要求分为 MUST、SHOULD、LATER、NON-GOAL，每条 MUST 编号并给出可判断的验收方法。
4. 定义 3–8 个 KPI 与红线，写入 docs/ACCEPTANCE.md。
5. 列出关键未知项和最小验证实验。
6. 建立必要的 PROJECT、ACCEPTANCE、STATE、ROADMAP。
7. 给出下一阶段最小计划及退出门禁。

不要立即大规模编码。
不要预建大量空模块。
不要进行无证据的架构重写。

对于低风险、可逆、且不影响外部合同的细节，可以采用合理默认值并记录；
对于目标、数据、安全、费用、公开接口和不可逆操作的关键歧义，先请求确认。

后续按阶段门禁推进，每个非平凡变更都保留验证证据。
未运行的测试明确标记 NOT_RUN，缺少条件明确标记 BLOCKED。
```

## 存量项目接入

```text
你是本仓库的工程师。这是一个已存在的项目，采用 ENGINEERING.md 的接入协议，
不重做整个项目：

1. 保全现场：保留现有代码、未提交修改、配置和证据。
2. 若当前 HEAD 不稳定，先切回最稳的 commit/tag。
3. 资产盘点：跑一遍，列出真正能跑的功能，每条变成一个粗粒度 golden 测试。
4. 粗测当前 KPI，记入 docs/BASELINES.md —— 这是第一个可对比基线。
5. 全绿后打 stable-<接盘日期>。
6. 已知坏处与缺失列成缺陷清单，按收敛协议"修/降/砍"三选一。
7. 建立真实验证入口（scripts/test.sh、scripts/bench.sh）。
8. 从此一切变更只走 feature / bugfix / optimization / refactor 四类流程。

不要以"引入流程"为名发动目录重排、模块重写、依赖替换的混合改造。
```

## 精简模式（小脚本 / 原型）

至少保留：**铁律 F1（绿基线）、F3（先证伪）、F14（卡住即停）、F2（回滚优先）**
+ `scripts/test.sh` + `CHANGELOG.md` + `STATE.md`，其余可裁。
