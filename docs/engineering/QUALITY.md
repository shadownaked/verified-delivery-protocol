# 质量与验证（QUALITY）—— ENGINEERING.md §6/§7 的展开

> **Verified Delivery Protocol (VDP) · 可验证交付体系 · v1.1**

> 本文件写"验证怎么做才有效"。铁律与门禁见 `ENGINEERING.md`。

## 1. 质量原则

质量必须同时覆盖：

1. **功能正确：**结果符合要求。
2. **失败正确：**异常不会变成静默错误、数据破坏或无限等待。
3. **非功能要求达标：**性能、资源、兼容性、安全等满足约定。
4. **使用可行：**别人能够安装、运行和排错。
5. **变化可控：**修改不会未经发现地破坏已有能力。

测试通过只说明测试覆盖的条件成立，不代表系统无缺陷。

## 2. 要求—实现—验证追踪

每条 MUST 至少关联一个验收项：

```text
REQ-需求
  ├── TASK-实现任务
  ├── TEST-自动或人工验收
  └── 发布记录中的实际结果
```

| 要求 | 验收场景 | 验证入口 | 最新证据 |
|---|---|---|---|
| REQ-001 | 核心成功场景 | 实际测试或操作说明 | 记录位置 |
| REQ-002 | 必要失败场景 | 实际测试或操作说明 | 记录位置 |

可以使用表格，不强制购买或搭建复杂管理系统。不能只建立"代码覆盖了多少行"的统计，却不知道用户要求是否被验证。

## 3. 测试层次

| 类型 | 主要验证对象 |
|---|---|
| 单元测试 | 纯逻辑、边界条件、状态转换 |
| 集成测试 | 模块、数据库、文件、外部接口等边界 |
| 合同测试 | 输入输出、错误类型、兼容性约定 |
| 验收测试 | 使用者的完整场景 |
| 回归测试 | 已修复缺陷和历史关键能力 |
| 故障测试 | 依赖失败、超时、中断、恢复 |
| 性能测试 | 时延、吞吐、内存、成本、资源上限 |
| 安全检查 | 权限、敏感数据、输入处理、依赖风险 |

不要求每个项目都建立全部目录或复杂测试框架，但必须按风险覆盖必要类别。

### 重要规则
- mock 通过不等于真实集成通过。
- 单元测试通过不等于完整场景可用。
- 高覆盖率不等于断言有意义。
- 自动测试不足的部分可以采用可重复人工验收，但必须明确记录。
- 关键验收应来自需求，而不是实现写完后反向编造。
- 对于关键缺陷，尽可能验证：故意恢复缺陷或在旧版本运行时，对应测试确实会失败。

### golden 场景集

每条 golden 登记：编号、名称、来源（哪次事故 / 哪条验收标准）、断言要点。
**只增不减**；修改或删除 golden 必须有 ADR。
三大来源：每个修过的 bug、每条验收标准、每次真实事故。

## 4. 缺陷修复流程

### 能稳定复现
1. 保留故障证据。
2. 建立最小复现。
3. 添加针对性测试。
4. **确认测试因目标缺陷失败，而非环境错误。**
5. 修复问题。
6. 确认测试通过。
7. 运行受影响的既有验证。
8. 将该场景保留为回归保护（通用场景同时登记为 golden）。

### 暂时不能稳定复现
- 先增加必要观测；
- 记录触发条件和失败频率；
- 使用可控实验缩小范围；
- 明确结论的不确定性；
- **不把"改后暂时没出现"报告为根因已确认。**

## 5. 已验证基线

基线不是"印象中不错的版本"，而是有证据的参考状态。

基线记录至少包含：代码提交 / 配置和行为相关输入 / 依赖及工具链 / 测试环境 / 测试场景 / 验证结果 / 性能或资源数据 / 已知限制。

对于行为受提示词、模型设置、规则文件、数据或工作流影响的系统，这些内容也属于版本和基线的一部分。

### 基线规则
- 保留最近一个可用的已验证版本。
- 新版本必须与既定基线比较。
- 不得通过直接改写基线掩盖退化。
- 允许经过批准的权衡，但要说明得到什么、失去什么。
- 历史基线已存在缺陷时，明确列出，不能伪称全绿。

## 6. 性能与稳定性评测

性能结论必须注明：测什么 / 在什么条件下测 / 样本量 / 成功和失败如何计入 / 与哪个版本比较 / 允许多大波动 / 是否存在外部环境干扰。

### 不能这样判断
- 一次很快，所以"性能优化成功"。
- 一次很慢，所以"代码一定退化"。
- 重跑二十次取最好的一次。
- 只统计成功任务，排除慢任务和失败任务。
- 用很小样本宣称可靠的高分位指标。

### 正确方式
- 固定代表性负载。
- 尽量保持环境一致。
- 进行足够重复（≥3 次取中位数）。
- 同时记录成功率、耗时和资源成本。
- 将随机波动与明确退化区分。
- 外部服务变化明显时，采用相近时段对照或其他控制方式。
- 样本不足时，明确标为探索性结果。

门禁应依据事先约定的阈值和容差，而不是机械要求每次运行都更快。

## 7. 超时、重试、取消和恢复

凡涉及外部依赖、长任务或可能阻塞的操作，应明确：单步预算 / 整体预算 / 最大尝试次数 / 重试由哪一层负责 / 取消如何传播 / 超时后的状态如何判断 / 是否可能重复产生副作用 / 如何返回部分结果或明确失败。

### 必须避免
- 多层分别重试导致次数相乘。
- 每次重试重新获得完整总预算。
- 只有局部超时，没有整体上限。
- 超时后直接假定外部操作未发生。
- 失败后盲目重复非幂等操作。
- 所谓恢复只是继续等待。
- 把"等待人工处理"伪装成持续运行。

关键预算必须由可执行机制保证，而不是只写在提示词或文档中。

如果被监控执行单元阻塞，监控机制仍须有能力发现并采取动作；不能把可靠性完全寄托于同一个已卡住的控制循环。

对应 golden 场景：**卡死必须触发恢复路径**。

## 8. 命令入口合同

项目应提供少量明确、可重复的操作入口。下表是**逻辑名称**，不是要求照抄不存在的命令。应使用技术栈原生任务系统实现，并在 README 填入真实命令。

| 逻辑入口 | 行为 |
|---|---|
| bootstrap | 安装或准备声明的依赖 |
| check | 格式、静态分析、类型等快速检查 |
| test | 默认快速测试（`scripts/test.sh`） |
| test-integration | 必要边界的集成验证 |
| test-acceptance | 关键使用场景验收 |
| build | 生成交付物 |
| smoke | 对交付物做最低可用性检查 |
| verify | 明确声明的一组综合验证 |
| bench | 性能测量（`scripts/bench.sh`，输出可记录数字） |
| clean | 仅清除声明为可再生的产物 |

要求：
- 失败返回非零退出状态或等价明确失败状态。
- 不得吞掉子任务失败。
- 缺少必需凭据时明确 BLOCKED 或失败，不得假通过。
- `verify` 必须说明包括和不包括什么。
- 真实环境验证与离线测试要可区分。
- `clean` 不得删除用户数据、源文件或未识别内容。

**`scripts/test.sh` 与 `scripts/bench.sh` 是硬依赖**：铁律 F1 绿基线、门禁清单第 1 项、optimization 流程都直接指向它们。最小可只含一条命令，但必须有。

### bench 入口契约

`scripts/bench.sh` 的最小契约（模板已内置实现；项目在 `docs/bench/benchmarks.yml` 声明自己的基准）：

- 未配置任何可运行基准 → 输出 `BENCH: NO_BENCHMARKS_CONFIGURED`，退出码 2（诚实拒绝：既不是成功也不是失败；此状态下 optimization 任务不得宣称完成测量）。
- 基准执行失败 → `BENCH: FAIL <名称>`，退出码 1；全部成功 → `BENCH: OK`，退出码 0。
- 每次运行把元信息与摘要落盘到 `.artifacts/bench/<UTC时间戳>/`（`meta.json` + `summary.md` + 各基准日志）；可用环境变量 `VDP_BENCH_EVIDENCE_ROOT` 重定向证据目录。
- optimization 流程（ENGINEERING.md §3.3）的 before/after 数字必须来自 bench 证据目录，不得手填。
- `scripts/test.sh` 检查 [9] 逐项校验本契约（存在性、`BENCH:` 前缀、退出码 ∈ {0,1,2}、拒绝理由明确）。

## 9. 把制度落实成机械约束

只有文档还不够。建立骨架时应把能自动化的约束落实到工具中。

| 规则 | 应落实的位置 |
|---|---|
| 代码风格一致 | 格式化工具 |
| 基本错误检测 | 静态分析、类型检查 |
| 历史问题不能复发 | 回归测试 / golden |
| 关键用户场景可用 | 验收测试 |
| 依赖可重建 | 配置和锁文件 |
| 失败不能假通过 | 脚本退出状态、结果协议 |
| 等待不能无上限 | 具名常量 + 超时 / 取消机制（门禁 grep 检查） |
| 修改不能直接破坏稳定版 | 分支、审查、合并门禁 |
| 交付来源可追踪 | 提交、构建标识、发布记录 |
| 故障后可以恢复 | 备份、恢复测试、回退流程 |
| 不误发秘密信息 | 权限、扫描、脱敏、发布检查 |

不要为了执行这张表再开发一套庞大的"工程平台"。优先复用技术栈现有工具。

## 10. 出现退化时的处置顺序

1. 停止新增功能和无关重构。
2. 保存当前代码、配置、日志和环境信息。
3. 确认退化的是功能、时延、成本、资源还是恢复能力。
4. 在可比条件下验证旧基线和当前版本。
5. 判断是代码、配置、依赖、数据还是外部环境变化。
6. 必要时回到已验证版本，先恢复可用性。
7. 缩小差异，定位最小致因变化。
8. 补回归保护。
9. 做最小修复。
10. 重新执行发布门禁。

可使用版本二分等方法，但应在安全、隔离、具备可重复判断条件的环境中执行。

**不能从"变慢了"直接跳到某个确定根因，也不能把大规模重写当成默认诊断工具。**

## 11. 完成定义

### 任务完成
- 目标实现，不含冒充完成的占位逻辑。
- 验收证据满足任务要求。
- 受影响回归已检查。
- 变更范围经过审查。
- 必要文档已更新。
- 风险和限制已记录。
- 回退方式明确。

### 版本交付完成
在任务完成基础上，还须：
- 本版本 MUST 全部满足。
- 发布阻断项清零。
- 实际交付物通过验收。
- 新环境使用流程通过。
- 已知限制被披露。
- 接收方能够获取和使用交付物。
- 维护、恢复、版本来源可追踪。
