# 开发流程（WORKFLOW）—— ENGINEERING.md §2 的展开

> **Verified Delivery Protocol (VDP) · 可验证交付体系 · v1.1**

> 本文件写"每个阶段具体做什么"。铁律与门禁摘要见 `ENGINEERING.md`，本文件不重复其效力。

## 1. 开发的基本模型

开发不是：

> 写代码 → 看起来差不多 → 不断优化 → 不知道何时结束。

正确模型是：

> 明确问题 → 定义验收 → 识别风险 → 建立可运行骨架 → 逐步完成真实能力 → 持续验证 → 冻结范围 → 实际交付 → 有边界地维护。

每轮变更遵循：

> **基线 → 假设 → 最小实验或修改 → 验证 → 决策 → 新基线。**

"科学"主要体现在：

- 结论可以被证据支持或推翻；
- 重要比较有明确基线；
- 尽量控制同时变化的因素；
- 记录环境和条件；
- 区分事实、解释与猜测；
- 承认样本不足和不确定性；
- 失败结果也被保留，而不是只展示成功结果。

阶段门禁是逻辑检查点，不是要求每个阶段都写大量文档。简单项目可以在同一天完成多个阶段。

## 3. P0：立项与现场盘点

### 目标
知道"正在解决什么问题"和"现在实际有什么"，并把愿望转换成可判断的完成条件。

### 新项目必须完成
- 明确目标使用者。
- 明确要解决的问题。
- 明确最终交付物形态。
- 明确运行环境和主要约束。
- 确认权限、时间、成本预算。
- 确认是否已有成熟方案可以直接满足需求。

### 已有项目额外完成
- 查看目录、入口、依赖、配置、测试和发布方式。
- 检查未提交修改。
- 找出当前可运行方式。
- 执行现有验证，区分已有失败和新增失败。
- 查找可能的历史良好版本，但不凭记忆宣布其为稳定版。

### 要求分级
- **MUST：**本版本不可缺少。
- **SHOULD：**有价值，但可以在明确记录后推迟。
- **LATER：**不属于当前版本。
- **NON-GOAL：**明确不做。

每条 MUST 必须有唯一编号，例如 `REQ-001`。每条至少说明：使用场景 / 输入和前置条件 / 预期结果 / 失败时应如何表现 / 验证方法。

### 必须区分三个层次
**项目不变量（INV）：**不能由 Agent 擅自改变的核心目标和约束。
**版本范围：**本版本承诺交付的能力。
**实现方案：**可在保持目标和合同的前提下调整。

不能因为某个实现困难，就悄悄修改目标或降低验收标准。

### 输出
- `docs/PROJECT.md`（初稿 → 批准）。
- `docs/ROADMAP.md` 首版。
- 初始 `STATE.md`。
- 验收清单和初始风险清单。

### 门 G0
1. 能够回答：谁使用它？解决什么问题？交付什么？如何判断有用？哪些操作没有授权？
2. 所有 MUST 都能通过自动测试或明确、可重复的人工步骤判断结果。
3. "更稳""更快""更优雅""通用性强"不能单独作为验收标准。

**禁止行为：**尚未理解现状，就进行全仓库整理、架构替换或大规模"优化"。

## 4. P1：设计与验收定义

### 目标
先验证最可能让项目失败的假设，而不是先完成最容易的部分；同时把 KPI 与红线定死。

### 典型风险
关键接口实际不可用 / 权限或部署条件不成立 / 性能或成本无法满足目标 / 数据无法可靠迁移 / 外部依赖不可控 / 方案需要不存在的技术能力 / 合规、许可或安全限制不允许。

### 可行性实验
为重要未知项设计小型实验，回答：假设是什么？什么结果支持它？什么结果推翻它？最少需要实现什么？最多投入多少时间和资源？实验结束后作何决策？

实验代码默认是实验代码。未经整理和验证，不直接转为正式系统基础。

### 设计最低内容
主要模块及职责 / 数据流 / 外部接口 / 关键状态和错误行为 / 安全边界 / 必要的性能与资源预算 / 测试方式 / 回退或替换路径。每个模块写明"不做什么"。

### KPI 与红线
在 `docs/ACCEPTANCE.md` 定义 3–8 个 KPI：功能（成功率）+ 体验（P50/P95 时延）+ 稳定（错误率 / 卡死率）+ 资源（可选）。每个 KPI 写明：定义、测量方法、基线值、目标值、红线（不可退化阈值）。

不能自动测量的 KPI，用固定场景清单人工测量并记录，同样入表。

### 门 G1
1. `docs/DESIGN.md` 与 `docs/ACCEPTANCE.md` 定稿，每个模块写明"不做什么"。
2. 不存在足以推翻当前方案、却仍未验证的关键假设。
3. 重大选型已有 ADR。

**禁止行为：**为尚未出现的需求提前构建插件体系、多层抽象、通用平台或复杂扩展框架。

## 5. P2：可运行骨架

### 目标
形成从获取代码到启动、测试、构建的最短闭环。骨架不是大量空目录，而是可以真实运行的最小系统。

### 必须完成
- 明确工具链和支持版本。
- 声明并合理锁定依赖。
- 提供可复制的安装步骤。
- 提供一个真实入口。
- 建立最低限度的测试。
- 建立检查、测试和构建入口（`scripts/`）。
- 建立基础日志和配置方式。
- 验证仓库没有依赖作者机器上的隐含文件或状态。
- 打通 walking skeleton（端到端空转）。

### 门 G2
在干净环境或等效隔离环境中：
1. 获取代码；
2. 安装依赖；
3. 启动最小系统；
4. 执行最低测试（`scripts/test.sh` 一键全绿）；
5. 生成预期构建物。

均可按照记录的步骤完成，且空流程可端到端演示。

**注意：**骨架跑通不等于业务功能完成。

## 6. P3：垂直切片

### 目标
让一个最小但有实际价值的使用场景，从输入到结果完整跑通。

不是先把所有数据库层写完，再写所有接口层，再写所有界面层；而是先交付一条完整能力。每片 ≤1 个会话。

### 要求
该切片必须经过必要的真实边界：实际输入 / 实际业务处理 / 实际存储或外部交互 / 实际输出 / 基本失败路径。

可以在开发测试中使用替身，但如果核心价值依赖真实系统，必须在授权条件下验证真实集成。

### 门 G3（逐片）
1. 门禁清单全过。
2. 一个新使用者按照现有说明，能够完成该场景，而不是必须由作者手工补环境、改数据或解释隐藏步骤。

**本阶段禁止：**做"优化"任务（除非某 KPI 已超标）；加 ACCEPTANCE 之外的功能。

## 7. P4：完成本版范围

### 目标
以可验证的小任务逐项完成 MUST 要求。

### 任务切分规则
一个任务应尽可能满足：一个主要目标 / 明确输入和输出 / 明确受影响范围 / 可单独验证 / 可单独审查 / 具有清晰回退边界。

不得把"修复故障、升级依赖、改目录、重写核心、增加功能"混成一次无法解释的修改。

### 每个任务执行
1. 建立任务记录。 2. 确认已验证基线。 3. 写验收方法。 4. 确定风险和停止条件。
5. 实现最小修改。 6. 运行相应验证。 7. 检查回归。 8. 更新必要文档。
9. 审查最终差异。 10. 在授权允许时提交。

### 并行规则
默认限制同时进行的主要变更数量。多 Agent 并行时：明确模块和文件所有权 / 使用隔离分支或工作区 / 明确集成负责人 / 不允许多个 Agent 无协调地修改同一组文件 / 每个分支通过验证不代表合并后自动通过验证。

### 门 G4
所有 MUST 已有实现和对应验证证据，不存在用占位逻辑伪装完成的部分。

---

## 8. P5：加固与稳定化

### 目标
停止扩张范围，确认已有能力在**异常条件**下仍然满足合同。

### 进入本阶段后
默认只允许：修复发布阻断问题 / 补足必要验证 / 修正文档 / 解决安全、数据、兼容性问题 / 错误路径加固。

新功能进入下一版本，除非负责人明确批准重新规划。

### 检查内容（按风险选择）
历史回归 / 错误输入 / 依赖不可用 / 超时与取消 / 并发与重复执行 / 部分失败 / 数据一致性 / 性能和资源消耗 / 安装与升级 / 权限与秘密信息 / 恢复与回退。

### 错误路径专项（旧 P4）
只处理：异常、超时、重试、看门狗、边界值、观测（日志 / 计时 / 计数）。每项加固行为必须有测试锁定。

### 测 KPI 入 `docs/BASELINES.md`
记录：日期 | commit | KPI | 数值 | 备注。这是后续反退化的比较基准。

### 门 G5
- ACCEPTANCE 全达标，加固行为有测试锁定。
- 本版 MUST 均有有效验收证据。
- 项目不变量没有被破坏。
- 没有未处理的发布阻断问题。
- 已知限制明确披露。
- 质量指标满足既定范围，或有正式批准的变更记录（ADR + 用户明示同意）。

## 9. P6：发布候选与实际交付

### 目标
验证"将交给使用者的东西"，而不是只验证开发目录中的代码。

### 必须完成
- 确定发布候选版本。
- 从干净环境执行安装与使用流程。
- 使用**真实交付物**运行关键验收。
- 检查 README 与实际操作一致。
- 检查配置样例、权限和依赖。
- 检查包内没有密钥、临时文件或不应发布的数据。
- 记录构建来源和交付物身份（commit / 构建标识 / 校验信息）。
- 验证升级、迁移、恢复路径，若适用。
- 写 runbook 并**实际照做一遍**能从零跑起来。
- 回滚方式**实际演练过一次**（能回到上一 stable tag）。
- 整理 CHANGELOG，打 tag。
- 形成发布记录 `docs/releases/`。

**测试完成后若继续修改代码或构建输入，必须重新执行受影响的验证。**

### 交付形态清单（按项目类型）
| 类型 | 交付物 |
|---|---|
| 库 | 可安装包、导入与使用示例 |
| 命令行工具 | 可运行程序、参数、退出码、安装说明 |
| 服务 | 部署产物、配置、健康检查、监控和运行手册 |
| 桌面 / 移动应用 | 安装包、支持环境、升级路径 |
| 自动化系统 | 可执行入口、权限说明、失败与人工接管机制 |
| 数据项目 | 数据或模型产物、版本、来源、验证与使用限制 |

### 交付后观察
向接收者提供实际产物和使用方式；说明已验证范围与已知限制；明确维护责任和反馈方式；对需要运行观察的项目，定义观察窗口、指标和回退触发条件。

部署、公开发布、付费资源创建、生产数据操作必须处于授权范围内。

### 门 G6
发布清单全过；实际交付物通过验收；接收者能够获取并实际使用交付物；若需要验收确认，已有明确确认记录。

**"代码已经 push"不等于"已经交付"。**

## 10. P7：维护、结项与归档

### 维护
- 缺陷进入任务系统（走 bugfix 流程）。
- 严重故障进入事故流程（`docs/templates/incident.md`）。
- 新需求进入下一版本（进 BACKLOG）。
- 依赖更新与安全修复经过验证。
- 定期评估兼容性、运行成本和弃用风险。

### 结项条件
- 本版本承诺已完成。
- 交付物可获取。
- 文档足够支持使用和维护。
- 残余风险已说明并处于接受范围。
- 后续工作有归属。
- **没有仅存在于某个 Agent 上下文中的关键知识。**

### 归档
- 标记维护状态和停止支持时间。
- 保留必要版本、发布记录和证据。
- 按规则处理访问权限、秘密信息、数据保留和外部资源。

**结项不要求所有未来设想都实现，也不要求证明不存在任何 bug。**

## 11. 变更控制与收敛机制

任何新增需求或"顺便优化"都先回答：
1. 它属于本版 MUST 吗？ 2. 不做会阻止交付吗？ 3. 现在做的收益是什么？
4. 会增加哪些风险？ 5. 是否挤占已承诺任务？ 6. 能否推迟到下一版？

默认决策：
- 阻止本版验收 → 纳入当前任务。
- 不阻止验收、低风险且成本明确 → 按授权判断。
- 扩大范围或改变合同 → 必须批准。
- 仅因"看起来更优雅" → 不自动纳入当前版本。

### 防止无休止修补
每个非平凡任务设定预算和诊断检查点。默认规则：

> 连续两轮修改没有增加新的可检验证据，或同一问题尝试超过 [30 分钟] / [3 种方法] 仍失败 → 暂停继续补丁，转为复现、测量、缩小范围或请求审查；仍不收敛则触发收敛协议（ENGINEERING.md §4）。

这是停止盲改的触发器，不是宣告问题无法解决。

## 12. 存量项目接入协议

采用新流程，不意味着先重做整个项目。顺序：

1. **保全现场。**保留当前代码、未提交修改、配置和必要证据。
2. **切回稳定点。**若当前 HEAD 已经烂，先切回记忆中最稳的 commit/tag。
3. **资产盘点。**列出当前真正能跑的功能清单（跑一遍逐条确认），每条变成一个粗粒度 golden 测试（跑通 + 关键断言即可）。
4. **粗测当前 KPI**，全部记入 `docs/BASELINES.md` —— 这就是第一个可对比的基线。
5. 全绿后打 `stable-接盘点日期`。
6. **建立最小项目合同**（`docs/PROJECT.md`），写清目前承诺哪些能力。
7. 已知的坏处和缺失 → 缺陷清单，按收敛协议"修 / 降 / 砍"三选一处理。
8. **恢复关键可用性**：优先最小修复或安全回退。
9. **建立真实验证入口**（`scripts/test.sh`、`scripts/bench.sh`）。
10. 按后续任务逐步补齐文档和结构。
11. **只有证据证明必要时，才重构。**（重构走 §3.4 流程）

不要以"引入科学流程"为名，再发动一次目录重排、模块重写、依赖替换和功能迁移的混合改造。

## 13. 完成判定标准

一个项目不是因为"代码写完了"而完成，而是因为以下问题有明确答案：

1. **目标：**解决谁的什么问题？
2. **范围：**本版本承诺什么，不承诺什么？
3. **合同：**什么结果才算正确？
4. **实现：**是否是真实实现，而非占位或演示？
5. **验证：**有哪些实际执行的证据？
6. **回归：**原本有效的关键能力是否保留？
7. **失败：**异常时是否有边界、明确结果和恢复路径？
8. **交付：**别人能否获取、安装并实际使用？
9. **维护：**出了问题谁接手、依据什么定位？
10. **收敛：**满足什么条件后停止修改并发布？

**把"已验证、可交付、可恢复"作为进度单位，而不是把"又改了多少代码"作为进度单位。**
