# 文件系统与变更管理（FILES）—— ENGINEERING.md §8 的展开

> **Verified Delivery Protocol (VDP) · 可验证交付体系 · v1.0**

## 1. 文件系统原则

### 源码、产物、现场数据分离
- 源码：应纳入版本管理。
- 构建产物：可再生，通常不纳入源码仓库。
- 日志与测试输出：进入明确的产物目录。
- 用户数据：使用独立、明确的数据位置。
- 秘密信息：不进入仓库。
- 临时实验：与正式实现隔离，完成后决定保留或移除。

不能把项目根目录当作所有文件的垃圾桶。

### 每个重要文件要有明确归属
新增文件前回答：
1. 它属于源码、测试、配置、文档还是产物？
2. 是否已有合适位置？
3. 是否引入重复事实？
4. 是否需要版本管理？
5. 生命周期是什么？

## 2. 命名规则

### 固定规范文件
采用本规范约定的固定名称：`ENGINEERING.md` / `AGENTS.md` / `STATE.md` / `README.md` / `CHANGELOG.md`，以及 `docs/` 下的 `PROJECT.md` / `ACCEPTANCE.md` / `BASELINES.md` / `DESIGN.md` / `ROADMAP.md` / `RUNBOOK.md` / `BACKLOG.md`。

### 其他文档和目录
默认采用清晰的英文 `kebab-case`：

```text
error-handling.md
release-checklist.md
data-migration/
```

### 源码命名
遵循语言和框架惯例，不强制全部使用同一种格式。技术栈已有规范布局时优先用原生布局。名 = 单一职责的可读名词；函数名用动词。

### 测试命名
`test_<对象>_<场景>_<期望>`

### 编号文件
```text
TASK-001-add-export.md
ADR-0002-select-storage.md
INC-0003-startup-failure.md
```

### 禁止
```text
final.py
final2.py
new-final-really.py
temp-fix-final.py
backup-old-copy/
utils2/
```

禁止 tmp / final / v2 / new / old / backup / xxx2 等无意义后缀；禁止成块注释掉的代码（历史交给 git）；禁止通过复制正式源码形成版本。

日期使用无歧义格式，例如 `2026-07-17`。跨时区运行记录应包含时区。

### 词汇统一
同一概念在代码、文档、测试中同名。

## 3. 模块组织

默认从最简单、能表达当前需求的结构开始。

- 模块按稳定职责划分。
- 外部依赖与核心规则应有清楚边界。
- 配置有集中定义和校验方式。
- 避免同一规则在多个模块中复制。
- 避免全局隐藏状态。
- 避免只为转发一次调用而增加多层抽象。
- 避免把所有不知放哪里的代码塞进 `utils`、`common`、`manager`。

当一个文件承担了多个可独立变化的职责时考虑拆分，而不是仅凭行数机械拆分。

抽象必须有明确的当前收益或已批准需求支撑。

## 4. 常量与配置

- 常量集中在一个配置模块，全大写或遵循语言惯例；**禁止散落的魔法数字**（尤其超时 / 重试 / 路径）。
- 依赖必须由正式配置声明。
- 支持锁文件的生态应合理使用锁文件。
- 记录支持的运行时和工具版本。
- 不依赖作者机器上未声明的全局包。
- 新依赖应说明用途、维护状态、许可和主要风险。
- 不因为只用一个小功能就随意引入庞大依赖。
- 也不为了"零依赖"无必要地重写成熟安全组件。

配置必须：
- 明确来源和优先级；
- 校验关键值；
- 提供安全默认值；
- 对缺失或非法值明确报错；
- 不把真实秘密值写入示例。

## 5. Git 与变更管理

推荐：
- 保留稳定、可追踪的主分支。
- 使用短期任务分支：`feat|fix|opt|ref|exp/<短横线描述>`。
- 一个提交尽量表达一个逻辑变化。
- 提交格式：`feat|fix|refactor|test|docs|chore: 一句话行为描述`。
- 保留发布版本和关键已验证基线。
- 合并前检查实际差异和验证证据。
- 标签：`v主.次.修`（semver）；每次门禁全绿另打 `stable-YYYYMMDD`。

示例：
```text
feat/task-012-add-export
fix/task-013-handle-empty-input
refactor/task-014-isolate-storage
```

提交说明应解释"改变了什么及为什么"，而不是只写 `update` / `fix` / `优化`。

没有远程 PR 系统时，可以用本地差异审查和任务记录完成同等职责，不必为流程额外搭建平台。

### 禁止默认执行
- 强制推送；
- 清空工作区；
- 删除未知文件；
- 覆盖他人修改；
- 重写共享历史；
- 自动丢弃未提交工作。

本地提交、推送和发布是不同权限，不得混为一谈。

## 6. 运行产物与证据

`.artifacts/` 可用于本地临时输出，但它不是长期证据保管制度。

发布和关键故障证据应：
- 保留经过脱敏的摘要；
- 指向可访问的完整报告；
- 记录版本与执行环境；
- 按项目规定保留；
- 避免仅依赖即将被清理的本地文件或过期链接。

没有 CI 或产物平台时，可以使用明确的交付目录或归档包，不必为了保存证据建设新系统。

## 7. 秘密信息

- 密钥、私人数据、敏感日志不得进入仓库或发送给外部服务。
- `.gitignore` 不是秘密保护机制。
- 已经被 Git 跟踪的秘密不会因为新增忽略规则而消失。
- 真正泄露的凭据需要撤销或轮换。
- 不要用过宽规则误排除测试夹具、交付文件或必要配置。

## 8. 清理规则

清理前分类：
1. 可再生产物：可按声明规则清理。
2. 过期实验：确认无引用后移除。
3. 正式功能：先影响分析和批准。
4. 未知文件：先识别，不自动删除。
5. 用户数据：按授权和保留策略处理。

"目录看着乱"不是删除内容的充分理由。
