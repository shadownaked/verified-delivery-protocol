## 0. 复核方法与边界

**只读保证**
- 全程未修改项目主体任何文件；所有脚本实跑均在隔离副本
  `.repo-meta/.TMP/review-repo/`（由 `git ls-files` 逐个 `cp -p` 复制，保留 mtime）中进行。
- 复核结束时 `git status` 仅显示 `.repo-meta/` 下的新增复核产物（见 §7）。

**为什么用副本而不是原地跑**
`scripts/bench.sh` 会写 `.artifacts/bench/<ts>/`、`scripts/test.sh` 检查 [9] 会在项目内建临时目录、
`scripts/build-complete.sh` 会重写 `dist/`。为此全部在副本中执行；`test.sh` 的
`dist` 新鲜度检查依赖 mtime，故用 `cp -p` 保留时间戳，而不是 `git clone`（clone 会把所有文件
mtime 归零，使检查 [6] 失去意义）。

**环境**
| 项 | 值 |
|---|---|
| 平台 | Windows 11 |
| Shell | BusyBox ash 1.38（w64devkit），包与脚本按 POSIX 目标验证 |
| 工具 | busybox grep / find / awk / sed / wc、Git 2.x、Python 3.12（仅用于 YAML/JSON 语法校验） |
| 现状 HEAD | `b2b0136`，工作树干净 |

**复核手段**
1. 逐条对照审计 A–H 与"额外硬要求"，判定每个要求是否真实落地（不是看声明，是看文件与脚本行为）。
2. 独立重跑全部验证命令，并与交付总结的数字逐项比对。
3. 对新增检查项做**变异测试**：故意制造违规，看检查能否抓住（防"检查页存在但没检查"）。
4. 对检查项的**空集/环境失效**场景做反向测试（防假绿）。
5. 交叉引用审计：文档里每个 `§`、铁律编号、文件路径、检查编号是否真实存在。

## 4. 发现清单

### S1（阻断）— 无

### S2（应修复）

#### S2-1 检查项在"范围枚举失效"时对空集判 PASS，且与健康态汇总完全相同（假绿）

- **现象**：`test.sh:38` 用 `find` 枚举模板主体 md；`[5]`（VDP 标识覆盖）、`[7]`（空目录）、
  `[8]`（旧名残留）、`[10]`（异常标记）都只在"集合非空"时才有判别力。一旦 `find` 失败或返回空，
  四项全部 PASS，汇总输出 `PASS: 49 / FAIL: 0`，与健康基线**完全一致**。
- **复现**：把 `SCOPE_MD` 的 `find` 换成一个失败命令后运行（模拟 `find` 不可用/被 Windows
  `C:\Windows\system32\find.exe` 抢占——后者不支持 `-not -path`，在这个仓库里就是这个行为）。
- **证据**：`02-test-sh-scope-empty-false-green.log`：
  ```
  PASS  VDP 标识覆盖 (0/0)
  PASS  无空目录
  PASS  旧名'统一开发体系'残留数 (0)
  PASS  [10] 异常占位标记
  PASS: 49    FAIL: 0
  结果: PASS
  ```
  对比健康态（`01-test-sh-pristine.log`）：`PASS  VDP 标识覆盖 (34/34)`，其余同上。
- **影响**：这正是审计"不允许因为脚本存在但什么都没做而欺骗 gate"要防的形态，只是发生在检查器一侧。
  另外 `test.sh` 的前置检查只验证 `find` **存在**，不验证其能力（`-not -path`），所以在 Windows
  或裁剪版 BusyBox 上会静默降级为盲绿。
- **附注（F12 相关）**：v1.0 的 `[5]` 曾断言"含 VDP 标识的 md 数 = 26"（硬编码，故在文件数变化时
  恒红，是缺陷）；v1.1 换成纯比例覆盖，取消了任何数量下限，等于把"恒红假阳性"换成了"可空转假阴性"。
  `CHANGELOG.md` 的 Compatibility 段只写了"检查更严"，未记录这条断言形态变更。
- **建议**：① `[5]` 增加最低数量断言（如 `TOT >= 30`）；`[7]`/`[8]`/`[10]` 增加"扫描文件数 > 0"断言；
  ② 前置检查里对 `find` 做能力探测（`find . -name "*.md" -not -path "./x/*" >/dev/null 2>&1 || BLOCKED`）；
  ③ 摊薄到一条统一的 `SCOPE_EMPTY → FAIL/BLOCKED` 判定。

#### S2-2 检查 [6] 只比对 30 个嵌入源中的 8 个，其余 22 个改动后产物过期不被发现

- **现象**：`test.sh:114` 的 mtime 比对清单只列 `ENGINEERING.md AGENTS.md WORKFLOW.md QUALITY.md
  OPERATIONS.md SECURITY.md AUTHZ.md _PACKAGE_README.md`；而 `build-complete.sh` 嵌入 30 个文件。
- **证据**：`04-mutation-tests.log` M1/M2：
  - `touch docs/BASELINES.md`（在 dist 内、不在清单内）→ `PASS 产物未过期`，整体仍 49/0；
  - 对照 `touch docs/AUTHZ.md`（在清单内）→ `FAIL 产物已过期`，48/1。
- **影响**：`FILES.md`/`CHANGELOG.md`/`docs/templates/*` 改动后 `dist/` 可静默过期，而 docstring
  声称"产物过期会被抓出来"。
- **建议**：从 `build-complete.sh` 的 `FILES` 列表派生比对集合（单一事实源），或反过来让
  `build-complete.sh` 输出一份 `dist/.sources` 清单供 [6] 读取。

#### S2-3 三个脚本在 git 中无执行位，检查 [9] 也未验证"可执行"（审计 B1 明确要求）

- **证据**：`git ls-files -s scripts/` → `100644` ×3。POSIX 检出后 `./scripts/bench.sh` 会
  `Permission denied`；而审计给的验证命令写作 `./scripts/test.sh`。`test.sh:140` 与 `[1]` 均只查 `-f`。
- **附带**：副本中能 `./scripts/bench.sh` 成功，是因为 Windows 文件系统上 `cp -p` 得到的是无执行位
  语义的全权限文件，**不能**用来证明 POSIX 可执行。
- **建议**：下次提交时 `git update-index --chmod=+x scripts/*.sh`；`[9]` 增加可执行判定
  （`[ -x scripts/bench.sh ]`，在无执行位语义的平台记 `N/A` 并在输出里明示）。

#### S2-4 自检会真的执行下游配置的基准（自检继承基准的耗时/副作用/外部依赖）

- **现象**：`test.sh:144` 以脚本内固定的 `CONFIG`（`docs/bench/benchmarks.yml`）调用 `bench.sh`。
  在本模板下 `run` 为空所以只走退出码 2 路径；但下游一旦配置真实基准，
  `sh scripts/test.sh`（`ENGINEERING.md` §5 要求"开工必跑"）就会执行真实基准负载。
- **影响**：自检可能变慢、失败于与体系无关的外部依赖，甚至产生写操作；且 `bench` 的
  `seconds` 噪声会污染"绿基线"判断。
- **建议**：`[9]` 用契约专用临时配置（复制 `benchmarks.yml` 后清空 `run`，或在临时目录生成
  最小配置并以环境变量覆盖 `CONFIG`），只验证契约，不执行真实基准。
